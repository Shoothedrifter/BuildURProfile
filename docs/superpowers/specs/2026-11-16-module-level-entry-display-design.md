# 解析与补充页：模块级条目展示设计

## 意图

删除“解析与补充”页每个条目的“展示此条”勾选框。用户开启一个模块后，该模块下的全部非空条目默认进入作品集；用户不再逐条选择，避免忘记勾选后在“确认并选择风格”处被阻塞。

## 系统现状与根因

- Python Agent 生成的模块 `visible`、条目 `included` 和字段 `included` 默认均为 `false`。
- Web 编辑器提供三层展示控制：模块“显示”、条目“展示此条”、字段“展示”。
- `projectConfirmedResume` 只投影 `visible` 模块中的 `included` 条目，再只投影条目内 `included` 字段。
- 基本信息确认检查也先过滤 `item.included`。因此即使模块已显示、内容也已核对，漏点“展示此条”仍会导致确认失败。

## 目标行为

- 模块“显示”是条目是否进入作品集的唯一控制：
  - 模块开启：该模块下全部非空条目进入生成投影。
  - 模块关闭：该模块下全部条目不进入生成投影，但草稿数据保留。
- 删除所有条目卡片上的“展示此条”勾选框。
- 条目仍可编辑、排序、拆分、合并、移动和删除。
- 基本信息、求职意向中的字段级“展示”控制继续保留，用于姓名、电话、邮箱、薪资等字段的精细隐私确认。
- 基本信息的姓名/联系方式检查不再依赖条目 `included`，只依赖模块可见且对应字段已选择并有值。
- 旧草稿与 Agent 私有协议继续保留 `item.included` 字段，避免 Schema、Python 合同和既有数据迁移；该字段成为兼容字段，不再决定条目展示。
- 旧浏览器解析兼容入口不在本次范围内；本次只修改新版 Agent 的“解析与补充”页。

## 实现方案比较

### 方案 A：仅隐藏勾选框

不改投影逻辑，只隐藏 UI。旧草稿和 Agent 新草稿的条目仍是 `included: false`，用户将无法让条目进入生成。不可采用。

### 方案 B：移除所有 `included` 字段

同时升级 TypeScript Schema、Python Pydantic 合同、数据库草稿和候选合并逻辑。语义最干净，但会扩大为跨语言合同迁移，风险和成本远超本次交互修复。

### 方案 C：模块决定条目、字段继续精细控制（采用）

保留合同兼容字段，UI 删除条目勾选框，投影与基本信息检查忽略 `item.included`。这直接解决痛点，不破坏 Agent 协议，也保留字段级隐私控制。

## 验收标准

1. “解析与补充”页不存在“展示此条”控件。
2. 可见模块中的条目即使历史值为 `included: false`，也会进入确认后的作品集合同。
3. 隐藏模块中的条目不会进入确认后的作品集合同。
4. 基本信息条目的 `included: false` 不再阻塞姓名与联系方式检查；字段自身未选择时仍需明确选择。
5. 保存旧草稿、重新解析候选和跨语言合同不需要迁移。
6. `npm test`、`npm run build` 与 `git diff --check` 通过。

## 非目标

- 不删除字段级“展示”控制。
- 不改变模块初始隐藏策略。
- 不修改旧浏览器解析兼容流程。
- 不升级 `resume-draft-v2` Schema 版本。
