# 简历编辑与重解析 P1 Spec（审阅稿）

**日期：** 2026-11-13
**依据：** [前三页 PRD](../PRD/11.7-前三页prd制作.docx) 3.4–3.6、3.9，[既有阶段计划](../agent/agent-resume-parsing-plan.md)及 [P0 归档](../archive/2026-11-11-figma-resume-p0.md)。Figma 页面作为交互参考；服务端权限、固定展示骨架和版本合同以仓库现行规则为准。

## 1. 目标、现状与边界

P1 让用户在核对页可靠地整理简历：调整模块和条目顺序、手动拆合经历、自动保存、从历史版本恢复，并选择覆盖或补空方式重新解析原 PDF。扫描型 PDF 增加用户主动选择的本机 OCR 路径。作品顺序应与用户确认的顺序一致，原 PDF 仍可对照，用户补充的图片、链接和文字继续随条目流转。

P0 已完成稳定 `itemId`、十模块、条目上下移动、跨模块移动、显式保存、原件对照、补充资产、`resume-v2` 作品闭环。“重新解析”目前复制原 PDF 生成另一份草稿；没有合并到当前草稿的模式。P1 不重复建设这些功能，也不改变已有作品和付费资格。

**P1 交付分三段：** P1a 编辑及展示顺序；P1b 自动保存、版本历史和重解析合并；P1c 用户选择的 OCR。每段独立验收，全部完成才称 P1 完成。P1c 的本机运行环境和容器依赖须一起交付，不能只留下未配置的接口。

**不进入 P1：** 任意 HTML/CSS/JS 模板、账号协作、扫描件自动送第三方、历史作品反向更新、无限期原件保存。PRD 的“添加自定义模块”需要突破固定十模块及映射合同，本轮提供“其他内容”中的自命名条目，真正第十一个模块留待单独合同设计。此取舍请在审阅时重点确认。

## 2. 用户行为

### 2.1 顺序、拆分与合并

十个系统模块都可在编辑页通过拖拽手柄和键盘上移/下移排序，系统模块不能删除；模块隐藏后仍保留顺序和私有内容。条目在模块内既可拖拽也可用现有上下按钮排序；跨模块移动沿用现有操作。展开和导航状态不影响保存顺序。空模块留在核对页，作品只显示有内容且可见的模块。

四类多条经历（工作、项目、荣誉、校园）可“拆分此条”或“与下一条合并”。拆分由用户选定段落边界并预览结果，系统不按换行自动把一句话拆成独立经历；至少生成两条非空内容。原条目 `itemId` 保留给第一段，新段生成新 ID；原补充文字、链接、图片只留在第一段，第二段初始为空，用户可随后移动。两段均继承相关来源块作为私有核对线索，并标为待核对。合并时保留前条 `itemId`，按原顺序以换行连接正文、去重来源 ID；两条补充信息并排展示给用户选择归属，不静默丢失。图片总量与单条 6 张限制在确认前检查，超限需用户先调整。删除或合并后的图片仍遵循已有私有资产回收规则。

### 2.2 自动保存与冲突

编辑后 800 ms 防抖保存；图片和链接变更在操作结束后立即请求保存。每份简历同一页面只允许一个 PATCH 在途；在途期间的新编辑合并进下一次保存。服务端继续以 `revision` 进行乐观锁校验，不能用最后写入覆盖他人/另一标签页的版本。状态显示“保存中… / 已保存 HH:mm / 保存失败，点击重试”。

未保存变更仅缓存在当前浏览器的 IndexedDB，按 `resumeId`、原始 `revision` 和会话分区；本地副本不保存 PDF 字节、来源块正文或图片字节，保留最多到原件 30 天到期。断网时缓存并在恢复网络后尝试串行重试；若服务端 revision 已变化，停止自动提交，展示差异入口，由用户选择重新加载或复制当前文字后手动处理。页面离开前若仍有未保存变更，显示失败挽留提示；保存成功后清理对应本地副本。删除简历、会话变更或到期时清理本地副本。显式“保存草稿”仍可用。

### 2.3 历史与重新解析

服务端保留当前草稿加最近 10 个已提交的前版本，记录版本号、保存时间和操作类型，不记录 PDF 字节；只允许原会话查看与恢复，恢复生成**新 revision**，不回退计数。历史版本与原 PDF 同时到期或用户删除时清理。用户可预览版本差异再确认恢复，恢复也走同一 `revision` 冲突校验；历史图片须保持可读或明确提示已释放，不能产生悬空引用。

重新解析原 PDF 必须让用户选择“覆盖当前内容”或“仅补充空白字段”。启动前先保存当前修改并记录基准 revision；解析结果先作为独立的待应用候选任务，不改原简历的 `SUCCEEDED` 状态或当前草稿。覆盖保留可预览的历史版本，替换条目及顺序；补空保留用户编辑过的字段、条目顺序、显示选择和补充资产，仅填充真正空白的字段和未被用户删除的空模块。相同来源块可稳定匹配时沿用旧 `itemId`；不能可靠匹配的候选作为新条目并标待核对，不覆盖旧条目。完成时若当前 revision 已变，返回冲突并让用户重新审阅，不自动合并。失败、取消或超时不改动原草稿。P0 的“新草稿副本”路径保留为兼容入口。

### 2.4 OCR

仅在文本提取失败或混合 PDF 中检测到无文字页时展示“尝试 OCR”；用户明确选择后才处理无文字页。优先采用本机 PDF 渲染与 Tesseract 中英文 OCR，页面图像和识别文字不发送给新的第三方。[pypdfium2](https://pypi.org/project/pypdfium2/) 可将 PDF 页渲染成图像，[pytesseract](https://pypi.org/project/pytesseract/) 提供带框和置信度的识别结果；具体版本、系统语言包和许可证须在实施时锁定与验证。OCR 词/行结果转换为带页码、边框和阅读顺序的私有 `ResumeSource` 块，保留 `ocr` 来源与置信度；不得将 OCR 低置信度内容直接当作已确认事实。混合页保留原可提取文本，仅对无文字页补 OCR；重复文字去重。OCR 不可用、超时、无结果时给出可重试的专用错误，原件仍能预览。原上传 10 MB、1–20 页与 30 天保留期不变；OCR 任务同样遵循租约、取消、限流、清理及日志脱敏规则。

## 3. 合同、映射与安全

- 私有草稿增量升级为 `resume-draft-v2`：显式模块/条目 order、字段级用户编辑标记、条目继承关系及来源类型；只用于核对与合并。旧 `resume-draft-v1` 在读取时规范化，旧任务继续按其原版本完成。
- 确认展示合同升级为 `resume-v3`：以有序 sections/items 为真相，仍只包含已选展示内容及作品资产 ID。版本化的生成 brief、`DesignConfig`、Python `resume.compose` 和工作流同步升级；`resume-v1/v2` 旧项目及正在运行的任务可继续读取，不在原版本上悄悄改顺序语义。
- 生成只读已保存且 revision 匹配的确认投影；PDF 原文、来源 ID、OCR 坐标、私有历史、未选字段和本地缓存均不得进入生成配置、checkpoint、分享或 ZIP。展示继续使用固定 Marquee + StackedCards 与三种皮肤，项目编辑不能改变支付事实。
- 排序和拆合后每个图片 ID 仍需属于当前会话与简历，且已被当前已确认条目引用；跨会话、过期、删简历与历史恢复越权一律拒绝。新接口沿用 CSRF、服务令牌、有效租约及有界请求大小。

## 4. 验收与发布条件

用合成 PDF 覆盖：原文与自定义模块顺序、键盘与触屏排序、拆合后的条目和补充资产、两标签页 revision 冲突、断网恢复、最近 10 版恢复、重解析覆盖/补空/失败隔离、扫描/混合 PDF OCR。预览、分享快照和 ZIP 的顺序及文字一致；原 PDF 对照仍在。所有测试只用合成简历；真实简历和密钥不得入库或进日志。

按 AGENTS.md 运行 Web、build、服务端、Agent、Skills 检查；OCR 若改 Docker/编排，还须构建两端镜像并验证 Compose 健康检查、持久卷和重启。正式发布前需要本机 OCR 依赖在目标系统可用的证据；真实模型、支付及公网回调仍属于另行上线验收。

## 5. 方案比较与本稿选择

直接扩写 `resume-v2` 和 `resume-draft-v1` 文件少，但旧生成任务会在相同版本下读到不同顺序规则，重解析也缺少可审计的用户编辑标记。全新编辑器和任意模块体系自由度高，却会重做 P0 已验证的资产和权限链路。**本稿选择版本化增量合同**：复用 P0 编辑、队列和资产，新增私有编辑元数据与公开有序合同；代价是跨 TS/Python/Schema/导出的同步迁移和兼容测试。
